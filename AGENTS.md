# Daily Tracker Supabase

Repositorio backend exclusivo de mdch2/daily-tracker-supabase. Documentación en español, código en inglés; pnpm exclusivamente.

- Este repositorio posee esquema PostgreSQL, migraciones, RLS, funciones, triggers, snippets, seeds, Edge Functions y configuración Supabase.
- La app móvil vive en mdch2/daily-tracker. No añadir UI ni código móvil aquí; no crear SQL o infraestructura backend allí.
- Conservar las migraciones transferidas sin editar su historia. Nuevos cambios de base requieren migraciones incrementales y pruebas reales de dueño, otro usuario y anónimo.
- No publicar secretos ni datos personales en fixtures/logs. Solo datos sintéticos. No aplicar cambios remotos sin una tarea que lo autorice.
- Comandos locales: pnpm db:start, pnpm db:reset, pnpm db:test, pnpm db:types. db:reset destruye datos de la instancia local; no ejecutarlo sobre datos que deban conservarse.
- pnpm db:types genera types/database.types.ts desde PostgreSQL local; conserva el artefacto anterior si falla. No sustituirlo por tipos escritos a mano ni afirmar generación si PostgreSQL no responde.
- Entregar ese artefacto a la app mediante su comando pnpm db:types. No importar archivos fuente entre repositorios ni mantener migraciones duplicadas.
- Verificar migraciones y RLS en PostgreSQL; los mocks móviles no prueban seguridad. Reportar resultados y bloqueos con precisión.

## Normas obligatorias de autorización y RLS

La política detallada y la matriz vigente están en [docs/security.md](docs/security.md). Se aplican a toda entrega, incluidos MVP, scripts y RPC.

1. **Denegar por defecto.** Toda tabla de aplicación expuesta debe activar RLS en la misma migración que la crea y antes de conceder acceso. Definir una matriz por objeto, rol y operación; una operación sin necesidad actual no recibe GRANT ni política. Nunca depender de permisos automáticos de Supabase.
2. **Privilegios y filas son controles distintos.** Revisar GRANT/REVOKE para PUBLIC, anon, authenticated y cualquier rol servidor autorizado. PUBLIC significa todos los roles. Conceder solo operaciones y columnas necesarias; nunca ALL para clientes. No dar CREATE, TRUNCATE, REFERENCES ni TRIGGER a clientes. No modificar permisos de esquemas administrados por Supabase por omisión.
3. **Propiedad e identidad confiables.** Obtener la identidad de auth.uid(), exigir que exista y comparar con el propietario de la fila. No confiar en un user_id del payload, user_metadata/raw_user_meta_data ni banderas editables. Usar TO authenticated y (select auth.uid()) cuando el valor sea independiente de la fila. La clave publishable y una ruta protegida no autorizan acceso.
4. **Políticas por operación.** SELECT y DELETE usan USING; INSERT usa WITH CHECK; UPDATE usa ambos y necesita la política SELECT correspondiente. Evitar FOR ALL y USING (true)/WITH CHECK (true) en datos privados. Revisar el conjunto de políticas: las permisivas se combinan con OR y una política nueva puede ampliar acceso.
5. **Propiedad y campos de servidor protegidos.** El cliente no transfiere propietarios ni escribe created_at/updated_at. Limitar escrituras por columna y restricciones/triggers según el contrato. Validar referencias entre entidades privadas mediante pertenencia, FKs compuestas u otra garantía equivalente; una FK simple no verifica propiedad. Indexar las columnas usadas por las políticas cuando lo requiera el acceso; no duplicar la PK.
6. **Anónimo cerrado mientras no haya contrato.** anon no accede a datos privados. El acceso sin registro y Supabase Anonymous Sign-Ins siguen pendientes; estos últimos usan authenticated y necesitarán reglas explícitas antes de habilitarse. No habilitar políticas públicas como atajo para errores de permisos.
7. **Funciones y vistas sin vías alternativas.** Preferir SECURITY INVOKER. SECURITY DEFINER requiere una necesidad concreta, privilegios mínimos, SET search_path = '', nombres calificados y revisión de autorización. Helpers internos en private, fuera de los esquemas API, sin EXECUTE de clientes. Las RPC reciben EXECUTE explícito por firma. Las vistas expuestas deben usar security_invoker = true y respetar los permisos/RLS de sus tablas; las vistas materializadas requieren un contrato de acceso propio. RLS no protege por sí sola funciones ni vistas que ejecutan como propietario.
8. **Roles privilegiados solo en servidor.** service_role, BYPASSRLS, superusuarios y propietarios pueden omitir RLS. Nunca enviarlos al móvil ni usarlos para validar aislamiento. Toda operación privilegiada debe justificar quién la invoca y qué identidad/recursos autoriza; no confiar en un ID recibido del cliente.
9. **Permisos nuevos explícitos.** Las migraciones de aplicación se ejecutan como postgres. Mantener revocados sus permisos automáticos de tablas, secuencias y funciones en public/private, incluido el EXECUTE global de PUBLIC para funciones nuevas. No basta revocarlo por esquema. Otro rol creador o un esquema nuevo requiere revisar sus propios defaults; no alterar roles internos de Supabase sin una necesidad documentada. Los defaults no corrigen objetos existentes: revisarlos explícitamente.
10. **Pruebas reales obligatorias.** Cada cambio de autorización incluye pgTAP sobre PostgreSQL real con propietario A, usuario B y anon, comprobando operaciones permitidas y denegadas, JWT ausente, escrituras cruzadas, columnas protegidas y funciones expuestas según aplique. Ejecutar como los roles cliente, nunca solo como postgres/service_role. Probar creación desde cero y actualización incremental sin pérdida de datos; fixtures sintéticos en transacciones con rollback. No declarar seguridad verificada si no se ejecutaron las pruebas.
